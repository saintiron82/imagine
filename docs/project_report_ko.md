# Imagine 프로젝트 종합 보고서

**작성 기준일**: 2026-04-06  
**기준 브랜치 상태**: 로컬 저장소 스냅샷 기준  
**현재 판단**: 코어 아키텍처는 완성 단계, 제품화와 품질 튜닝은 진행 중

---

## 1. 프로젝트 개요

Imagine은 PSD, PNG, JPG 같은 시각 에셋을 파싱하고, AI 분석과 벡터화를 거쳐 검색 가능한 자산으로 전환하는 로컬 우선 멀티모달 에셋 인텔리전스 시스템입니다. 단순 파일명 검색이 아니라 시각적 유사성, 의미적 맥락, 텍스트 팩트를 함께 반영하는 Triaxis 검색 엔진을 핵심으로 합니다.

프로젝트의 목표는 다음 세 가지로 요약할 수 있습니다.

- 대규모 이미지/PSD 자산을 검색 가능한 구조화 데이터로 전환
- 로컬 단일 장비부터 LAN 분산 워커 환경까지 같은 파이프라인으로 확장
- Electron 데스크톱과 웹 모드에서 동일한 경험 제공

---

## 2. 현재 제품 상태 요약

현재 저장소 기준으로 보면 Phase 1~4.6은 명확히 완료되어 있고, 그 이후 기능도 일부는 이미 코드에 반영되어 있습니다. 특히 다음 항목은 실구현 상태로 확인됩니다.

- Triaxis 검색 엔진: VV + MV + FTS + RRF 융합
- FastAPI 서버 + React/Electron 클라이언트 듀얼 구조
- JWT/Firebase 기반 2계층 인증
- 분산 워커, 임베디드 워커, 워커 자원 모니터링
- WebDAV/NAS 원격 폴더 처리
- 도메인 기반 분류 프리셋과 관리자 UI
- 데이터베이스 리셋, 재시도, 무결성 점검 등 운영 기능

반면 아직 제품 완성도로 남아 있는 과제도 분명합니다.

- 라이트박스 뷰어, 검색 히스토리, 고급 정렬 등 UI/UX 고도화
- 비동기 DB writer, 대량 batch commit 등 파이프라인 병목 최적화
- 검색 품질 자동 평가와 융합 가중치 튜닝
- 설치 패키징, 자동 업데이트, 백업/복구 UX 완성

즉, 현재 Imagine은 “기술적으로는 이미 강한 코어를 가진 실전형 시스템”이지만, “상용 제품 완성도”를 높이기 위한 다듬기 단계에 들어와 있다고 보는 것이 정확합니다.

## 3. 핵심 아키텍처

### 3.1 인제스트 파이프라인

현재 파이프라인은 Parse → Vision → VV → MV 흐름을 기준으로 구성되어 있으며, `backend/pipeline/phase_runner.py`가 Vision/VV/MV 단계의 공통 실행 로직을 담당합니다.

```text
이미지/PSD 입력
  -> Parse: 메타데이터, 레이어, 썸네일, 구조 정보 추출
  -> Vision: VLM 기반 MC 캡션/태그/분류 생성
  -> VV: 시각 벡터 생성
  -> MV: 의미 벡터 생성
  -> DB 저장 및 검색 인덱스 반영
```

핵심 설계 특징은 다음과 같습니다.

- 단계별 저장: 장시간 작업 중간에도 결과를 누적 저장
- skip/retry 중심 설계: 이미 끝난 단계는 재실행 최소화
- 로컬/서버/워커 모드에서 같은 단계 로직 재사용

### 3.2 검색 엔진

검색 엔진은 세 축을 조합합니다.

- VV: SigLIP2 기반 시각 유사도
- MV: 텍스트 임베딩 기반 의미 유사도
- FTS: SQLite FTS5 기반 팩트 검색

최종 결과는 `backend/search/scoring.py`의 RRF 기반 융합으로 정렬됩니다. 구조적으로는 단일 축보다 확장성이 높고, 질의 유형에 따라 복합 성능 향상을 기대할 수 있습니다.

### 3.3 서버 및 실행 모드

`backend/server/app.py` 기준으로 현재 서버는 다음 구조를 가집니다.

- FastAPI 앱 진입점
- 로그인 이후 활성화되는 지연 초기화 구조
- AnalysisJobManager, 다운로드 풀, 파싱 풀, 워커 스케줄러, 하트비트 워치독
- 필요 시 Embedded Worker 자동 기동
- 라이선스/인증/파이어베이스 재등록 훅

이 구조는 단일 머신 실행과 서버-워커 분산 실행을 모두 포괄하도록 설계되어 있습니다.

### 3.4 프론트엔드

`frontend/src/App.jsx` 기준으로 현재 UI는 단일 검색 화면을 넘어 운영용 워크스테이션에 가깝습니다. 실제로 포함된 주요 페이지는 다음과 같습니다.

- Login
- Analysis
- Archiving
- Factory
- Worker
- Admin
- Settings
- Download
- Setup

Electron 모드에서는 로컬 서버 자동 기동과 IPC 브리지를 사용하고, 웹 모드에서는 HTTP API를 사용합니다.

## 4. 구현 기능 현황

### 4.1 이미 구현된 강점

- PSD 심층 파싱: 레이어, 텍스트, 폰트, 구조 정보 추출
- 멀티모달 검색: 텍스트, 이미지, 조합 검색
- 도메인 기반 분류: `game_asset`, `illustration`, `stock_photo` 프리셋

- 라이트박스 뷰어와 전문 탐색 UX

- 컬렉션/북마크/태그 일괄 편집
- 비동기 DB writer 및 대량 commit 최적화
- 검색 품질 회귀 방지용 자동 벤치 파이프라인

## 6. 성능 및 검색 품질 평가

### 6.1 검색 품질

`benchmarks/results/precision_20260405_005630.md` 기준:

- DB 크기: 11,174 images
- 자연어 한국어 질의: 30개
- Triaxis `P@5 = 0.347`
- 단일 최고 축(VV) `P@5 = 0.187`
- 융합 향상폭: 약 `+85.7%`

해석은 명확합니다.

- 실제 체감 relevance 기준에서는 융합 검색이 단일 축보다 확실히 우수함
- 특히 브라우징 성격의 검색에서는 Triaxis가 제품 가치의 핵심 근거가 됨

### 6.2 전체 파이프라인 품질

`benchmarks/results/triaxis_fullpipe_20260404_221501.md` 기준:

- DB 크기: 11,174 images
- 질의 수: 50
- 단순 질의와 scoped 질의에서는 MV 단일축이 더 강한 구간 존재
- 복합 질의에서는 Triaxis 융합이 개선 효과를 보이는 구간 존재

즉, 현재 상태는 “융합이 항상 최적”은 아닙니다. 검색 품질은 이미 실사용 가능한 수준이지만, 질의 유형별 가중치 자동 조절과 fusion tuning이 다음 핵심 과제입니다.

### 6.3 처리 성능

기존 배치 벤치마크와 최근 문서들을 종합하면 다음 성향이 확인됩니다.

- Standard tier에서 배치 효율이 매우 높음
- Pro/Ultra tier는 모델 크기와 메모리 제약 때문에 batch 최적점이 더 민감함
- 분산 워커 구조는 병렬 확장성이 높지만 DB write 병목은 아직 남아 있음

즉, 추론 자체보다 저장과 큐 동기화가 다음 병목 구간입니다.

## 7. 리스크와 현재 이슈

### 7.1 문서 정합성

저장소에는 최신 구조와 맞지 않는 문서도 일부 존재합니다. 예를 들어 `QUICK_START.md`는 PostgreSQL 기반 구형 설치 흐름을 포함하고 있어 현재 SQLite 중심 구조와 맞지 않습니다. 운영 문서 체계의 정리가 필요합니다.

### 7.2 레거시 코드 잔존

`docs/issues/20260404_legacy_audit_results.md` 기준으로 큐/파이프라인 계열 레거시 코드와 미사용 프론트엔드 컴포넌트가 일부 남아 있습니다. 구조를 더 단순하게 만들 여지가 있습니다.

### 7.3 대시보드 SSOT 문제

`docs/issues/20260403_dashboard_rewrite_spec.md`는 큐 카운터와 진행률 산정의 진실 공급원 문제를 지적합니다. 운영 UI의 신뢰도를 높이려면 files DB 기준 단일 집계 구조로 정리하는 것이 필요합니다.

### 7.4 검색 품질 튜닝 필요

최근 벤치 결과는 Triaxis의 가능성을 보여주지만, simple/scoped 질의에서 항상 우세한 것은 아닙니다. 이 부분은 알고리즘 튜닝의 여지가 아니라 사실상 다음 단계 핵심 과제입니다.

## 8. 다음 우선순위 제안

현재 코드와 문서를 종합했을 때 우선순위는 아래 순서가 가장 합리적입니다.

1. 검색 품질 튜닝
   - 질의 유형별 fusion weight 재조정
   - offline benchmark 자동화
   - scoped/simple 질의에서 MV 우세 구간 분석

2. 파이프라인 병목 해소
   - async DB writer
   - bulk commit
   - queue/dashboard SSOT 정리

3. UI/UX 고도화
   - 라이트박스 뷰어
   - 검색 히스토리/정렬/단축키
   - 컬렉션/태그 일괄 편집

4. 문서/배포 정리
   - 구형 설치 문서 교체
   - Electron 배포 경로 표준화
   - 백업/복구/업데이트 흐름 정리

## 9. 종합 평가

Imagine은 현재 기준으로 “AI 검색형 이미지 자산 관리 시스템”의 핵심 기술 축을 대부분 확보한 상태입니다. PSD 파싱, 멀티모달 벡터 검색, 로컬 우선 실행, 분산 워커, 원격 폴더 처리, 데스크톱/웹 통합까지 이미 구현되어 있어 기술적 깊이는 충분합니다.

남은 과제는 기초 기술이 아니라 완성도입니다. 검색 품질 튜닝, 운영 지표 정합성, UI 체감 개선, 배포 경험 정리까지 마무리되면 팀/스튜디오 단위 실사용 제품으로 바로 이어질 수 있는 수준입니다.

현재 단계의 한 줄 평은 다음과 같습니다.

**“엔진은 강하고, 이제 제품을 다듬는 단계에 들어선 프로젝트”**입니다.
