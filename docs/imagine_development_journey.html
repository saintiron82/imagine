한 줄로 보면

Imagine은 처음부터 완성형으로 설계된 것이 아니라, 검색 실패, 큐 꼬임, GPU 메모리 문제, WebDAV 파일 준비 문제, UI 해석 혼동을 계속 만나면서 발전했다. 매번 증상을 로그와 벤치로 계측하고, 그 결과를 데이터 계약과 UI 문구, 스케줄러 규칙, 테스트로 고정한 뒤, 검증된 뒤에는 낡은 경로를 삭제하는 방식으로 여기까지 왔다.

  • 초기 목표: 개인 이미지/PSD/배경/아이템을 시각, 의미, 팩트로 찾는 로컬 검색.
  • 중간 병목: VLM 추론 속도, worker 분산, SQLite lock, queue count 불일치, 원격 파일 준비.
  • 핵심 해법: phase 분리, SSOT, worker capability scoring, benchmark baseline, query schema 통일.
  • 최근 초점: 검색 품질 평가가 진짜 검색 실패를 드러내도록 blind random benchmark와 0/1/2 rubric 정리.

반복된 개발 방법

Imagine 개발에서 반복적으로 보이는 실제 작업 패턴이다.

1. 증상 발견 검색이 이상함, worker가 멈춤, UI count가 틀림, benchmark가 헷갈림.
2. 계측 추가 timing log, phase log, diag_log, benchmark output, review CSV를 만든다.
3. 원인 분리 모델 문제인지, 데이터 계약 문제인지, UI 표현 문제인지 나눈다.
4. 계약화 schema, phase, query plan, scoring rubric처럼 코드가 따를 규칙으로 고정한다.
5. 검증 unit test, benchmark, review gallery, browser 확인으로 같은 문제가 재발하지 않게 한다.
6. UI 반영 사용자가 보는 화면에 phase, scope, score, failure reason을 숨기지 않는다.
7. 레거시 삭제 새 경로가 검증되면 fallback과 구형 manager, token, IPC 경로를 제거한다.
A

느낌보다 기준선

모델 선택과 검색 품질은 "좋아 보임"이 아니라 MC/VV/Triaxis benchmark, P@K, Recall, worker speed로 판단했다.

B

상태의 단일 진실

대시보드 count가 꼬이자 이벤트 누적 대신 files DB와 file_tasks를 기준으로 완료 상태를 다시 정의했다.

C

경계 분리

검색 문장 해석과 검색 실행, 파일 준비와 AI 분석, 서버 소유권과 worker 실행을 분리했다.

D

사용자 혼동을 설계 결함으로 처리

review UI가 caption 신뢰와 검색 relevance를 섞자, 점수 의미와 화면 문구를 다시 나눴다.

E

실패는 복구 정책으로 승격

WebDAV, parse fallback, SQLite lock, VLM crash는 try/except가 아니라 health check와 repair flow로 옮겼다.

F

벤치마크 독립성

최근 검색 평가는 이미지 내용을 보고 질문을 만드는 방식에서 벗어나, seedable blind random query로 전환했다.

핵심 전환점

큰 변화는 기능 욕심보다, 이전 구조가 실제 문제를 설명하지 못했을 때 일어났다.

VV/MV/MC에서 Triaxis로

이미지를 픽셀 유사도만으로 찾거나, AI caption만으로 찾는 방식은 각각 약점이 있었다. 그래서 시각 벡터, 의미 벡터, 텍스트/메타 FTS를 따로 만들고 RRF로 합치는 구조가 중심이 됐다.

작업 queue에서 Analysis Job으로

job_queue 이벤트만 보면 진행률과 완료 판단이 계속 흔들렸다. 이후 분석 단위를 job과 file task로 나누고, 완료는 실제 files DB 상태를 기준으로 보게 했다.

worker mode에서 capability scheduling으로

GPU 종류만 보고 phase를 고정하는 방식은 실제 속도와 맞지 않았다. local benchmark와 heartbeat throughput을 기반으로 worker가 잘하는 phase를 배정하는 쪽으로 바뀌었다.

자연어 검색에서 구조화된 plan search로

"세일러문 중에서 강이 보이는 것" 같은 쿼리는 자연어 전체를 검색어로 넣으면 scope와 find가 섞인다. 그래서 해석기는 scope, find, exclude로 나누고, 엔진은 이 조건만 실행하게 했다.

review UI는 평가 목적을 숨기지 않는다

"AI가 분석한 설명을 믿는가"와 "검색 결과 이미지가 맞는가"는 다른 질문이다. 최근 benchmark review는 이 둘을 분리하고, 기본 점수는 query condition 만족도로 해석한다.

검증된 뒤에는 과감히 삭제

legacy queue manager, worker token, setup UI, Cloudflare tunnel, 구형 IPC fallback은 새 구조가 검증된 뒤 제거됐다. 호환성보다 현재 구조의 명확성을 우선한 결정이다.

검색 품질 벤치마크가 바꾼 것

최근 Imagine의 핵심은 검색이 정말 좋아졌는지 판단할 수 있는 평가 체계를 만드는 것이다.

문제 바뀐 기준 의미
질문이 이미지에 맞춰 만들어질 수 있음 blind_random QuerySet, 고정 vocabulary, random seed 검색 엔진이 실제로 찾은 것인지, 질문이 쉬웠던 것인지 분리한다.
blind benchmark인데 scope가 보임 query_scope만 scope 표시 근거로 사용 folder/source metadata fallback 때문에 scoped 평가처럼 보이는 문제를 제거한다.
UI 문장 전체가 검색어로 들어감 must_terms, soft_terms, exclude_terms로 실행용 검색어 분리 리뷰어가 보는 자연어와 검색 엔진이 받는 조건어를 나눠 FTS 오염을 줄인다.
0/1/2 점수 의미가 애매함 2 전체 만족, 1 부분 만족, 0 핵심 불만족 "달과 별이 있는 마을"에서 달이 없으면 분위기가 맞아도 1이다.
대부분 2점이면 좋아 보임 scoring rule을 바꾸지 않고 hard case를 추가 시스템이 좋은 것과 benchmark가 쉬운 것을 구분한다.
현재 기준: Imagine의 검색 평가는 "AI caption이 그럴듯한가"가 아니라 "사용자가 낸 시각 조건을 실제 이미지가 만족하는가"를 우선 판단한다. caption/tag 품질 평가는 별도 신호로 남기되, 검색 relevance 점수와 섞지 않는 것이 최근 정리된 방향이다.
